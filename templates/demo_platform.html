Platform Demo: Custom Image Assembly

Declare your image configuration in a versioned build.yaml. Chainguard builds it, signs it, and your CI pipeline verifies it — zero CVEs, full audit trail.

⚠️

Today's Problem for Platform Teams

Platform and cloud engineering teams are maintaining golden images manually — a time-consuming, error-prone process that creates security and compliance debt.

Golden image toil

Platform team owns rebuilding and re-scanning base images. CVE patches require manual intervention every sprint.

No provenance

"We think it was built from this Dockerfile" isn't an audit answer. No cryptographic proof of what's in prod.

Drift across teams

Each team customizes the base image differently. No single source of truth. No consistent security posture.

📄

build.yaml — Versioned Image Configuration

The build.yaml lives in your repository alongside application code. It declares exactly what packages are in the image. Changes are reviewed in PRs, tracked in git history, and referenced in the image's SLSA provenance attestation. 

# build.yaml — checked into git, reviewed in PRs
# This file is the source of truth for the image.

contents:
  packages:
    - python-3.12
    - py3.12-pip
    - ca-certificates-bundle
✓ Package changes are git commits. Every change is reviewed, approved, and recorded. The SLSA attestation on the resulting image captures exactly what packages were declared — your auditor can verify what was in prod at any point in time.
🔨

One Command to Build

Apply the build.yaml with chainctl. Chainguard builds the image from source, signs it, and returns the digest. No Dockerfile. No docker build. No manual base image maintenance.

$ chainctl images repos build apply \ --parent $CHAINGUARD_ORG \ --repo python \ -f build.yaml ✔ Configuration validated ✔ Build triggered ✔ Image signed with Sigstore Cosign ✔ SLSA provenance attestation generated → cgr.dev/$ORG/python@sha256:a1b2c3d4...

The resulting image is rebuilt from Chainguard's hardened Wolfi base — only the packages declared in build.yaml, nothing else.

Automated: build.yaml Change → PR with Verified Digest

The GitHub Actions workflow triggers on any push to build.yaml. It builds the image, verifies the signature, scans for CVEs, and opens a PR with the new pinned digest — only if everything passes.

# .github/workflows/platform-build.yml (excerpt)
on:
  push:
    paths: [build.yaml]

steps:
  - uses: chainguard-dev/setup-chainctl@v0.2.2   # OIDC — no secrets
    with:
      identity: ${{ vars.CHAINGUARD_IDENTITY }}

  - chainctl images repos build apply -f build.yaml  # build + sign
  - cosign verify ...                                   # signature check
  - cosign verify-attestation --type sbom ...          # extract SBOM
  - cosign verify-attestation --type slsaprovenance ... # extract provenance
  - uses: anchore/scan-action@v3                       # Grype gate
    with:
      severity-cutoff: high
      fail-build: true

Evidence Bundle — Audit-Ready for Every Build

Every successful build uploads an evidence bundle as a GitHub Actions artifact (90-day retention). Pull it for any commit to answer an auditor's questions without chasing engineers.

🔐
signature-verify.json
cosign verification output — cryptographic proof the image is signed
📋
sbom.json
Full software bill of materials — every package and version in the image
📜
provenance.json
SLSA attestation — where it was built, when, and from what source packages
🛡️
grype-results.json
Grype scan output — 0 critical/high CVEs at time of build
⚙️
build.yaml
The declared image configuration — packages that produced this image
